wisp, the tiny test system, is the smallest Linux the lab can boot on each emulated architecture: a
kernel (`make tinyconfig` plus a few options) with a built-in initramfs that holds a single static
program as PID 1, built with the kernel's own nolibc instead of a C library. glibc and musl don't
support 32-bit SPARC V8; nolibc does (since Linux 6.16), so the same `init.c` runs on all four.

It boots straight from QEMU's `-kernel` on a serial console (no disk, no installer, no guest OS),
prints a banner, the kernel's `uname`, the CPU count and memory, runs a fixed compute loop with its
time and a checksum, prints one result line and powers the machine off. A run under TCG takes 2 to
3 seconds.

| Architecture | QEMU machine | Kernel image | Tier-2 kernel | PID 1 |
| --- | --- | --- | --- | --- |
| x86_64 | `pc` | 1,291,264 bytes | 1,836,032 bytes | 21,168 bytes |
| i386 | `pc` | 1,131,008 bytes | 1,675,776 bytes | 19,236 bytes |
| sparc32 | `SS-5`, `SS-20`, `SS-10`, `SS-4`, `SPARCClassic`, `SPARCbook`, `LX`, `Voyager` | 2,449,528 bytes | 3,311,560 bytes | 16,908 bytes |
| sparc64 | `sun4u` | 3,100,936 bytes | 4,117,384 bytes | 17,096 bytes |

The x86 images are compressed `bzImage`s; the sparc images are the stripped, uncompressed ELF the
OpenBIOS loader takes. PID 1 includes the interactive shell and the tier-2 checks below (before
the shell: 12,976, 8,908, 5,236 and 5,440 bytes; before tier 2: 17,072, 14,160, 8,716 and 8,904).
CI (`.github/workflows/wisp-boot.yml`) boots every architecture and machine in the table, tier 1
and tier 2, on pull requests that touch wisp or the QEMU build, and on main; the `LX` and the
`Voyager` need OpenBIOS patch 0027, in the published `pve-qemu-kvm` since 11.1.3-3+wsh9.

## What it is for

- **A smoke test of a QEMU binary.** Does this build boot Linux on this machine, write to
  its serial console, and power off? The checksum of the compute loop is the same on every architecture,
  so a CPU model that computes wrongly fails the run.
- **Comparing backends.** TCG (the JIT) against TCI (the TCG interpreter, the only backend QEMU
  has where it can't generate host code, such as a WebAssembly build), without a guest OS's own
  start-up time in the numbers.
- **The devices the QEMU patches touch** (tier 2): a raw disk on each disk controller, a NIC on
  QEMU's user-mode network and more than one CPU, each with its own result line.

## Modes

PID 1 reads `wisp=` from the kernel command line and picks one of three modes; the default (no
`wisp=`) is the batch compute-loop run described above.

| `wisp=` | What PID 1 does | Marker |
| --- | --- | --- |
| `shell` | starts the interactive shell on the serial console (see "Interactive mode" below) | none |
| `test` | runs `/test` from a second initramfs once, waits for it, prints its exit status and powers off | `WISP-TEST` |
| `run` | runs `/test` as a service, reaping any children it leaves behind, then reports its exit | `WISP-RUN` |

`test` and `run` both expect `/test` from a second, uncompressed initramfs that QEMU's `-initrd`
adds next to the built-in one; arguments after `--` on the kernel command line and the environment
reach it. `test` mode prints one line and powers off:

```
WISP-TEST v=1 exit=1 signal=0 ms=88
WISP-TEST v=1 exit=-1 signal=10 ms=72
```

`exit` is the exit code (`-1` when a signal killed it), `signal` the signal (sparc numbers:
`SIGBUS` is 10) and `ms` the time from `fork` to `waitpid`. `run` mode prints `WISP-RUN v=1
start`, keeps reaping children while the service runs, then reports its exit code, signal and
elapsed milliseconds before powering off; it is how the network demo below starts a long-running
service instead of a one-shot test.

## Interactive mode

`wisp=shell` on the kernel command line starts a small shell on the serial console instead of the
batch run; without it, nothing changes. It is meant as the base of a browser demo (QEMU as
WebAssembly with xterm.js), so it fits an 80 x 24 terminal and uses a few ANSI colours.

```sh
qemu-system-sparc -M SS-5 -m 128 -display none -nodefaults -serial stdio -monitor none \
  -kernel e2e/wisp/out/sparc32/kernel -append "console=ttyS0 wisp=shell"
```

| Command | What it does |
| --- | --- |
| `help` | the list of commands |
| `info`, `uname` | architecture, kernel, CPUs, memory, uptime, PID |
| `bench` | the batch run's compute loop with its CRC, time and KiB/s |
| `crc <n>` | the loop's CRC after `n` rounds |
| `mandel` | an ASCII Mandelbrot set (78 x 20) in fixed-point 32-bit integer math |
| `fbtest` | draw colour bars on `/dev/fb0` and print the mode (framebuffer tier only) |
| `mandel fb` | draw the Mandelbrot set at the framebuffer's native resolution (framebuffer tier only) |
| `keytest` | print key codes from a keyboard until Esc or a ten-second timeout (framebuffer tier only) |
| `endian` | a byte-order guessing game: guess the 32-bit word *this machine* reads from a round's four bytes (the answer depends on the architecture under test) |
| `disk`, `net`, `smp` | the tier-2 checks below, on the devices QEMU was started with |
| `banner` | the logo |
| `clear` | clears the screen |
| `poweroff`, `reboot` | power off or restart (`reboot` on sun4u needs a package whose OpenBIOS has patch 0030; before it the kernel panics with "Reboot failed!") |

The console stays in the kernel's canonical mode: the TTY line discipline echoes and edits the line
(Backspace, Ctrl-U, Ctrl-W, Ctrl-C). `run.py --shell` drives the shell over the serial console on
all four architectures and checks every answer, down to each character of the Mandelbrot set; CI
runs it after the batch boots. On sparc, `init.c` brings its own `_start`: nolibc's lost the
kernel's arguments and environment there, so until now `loops=` never reached PID 1 on sparc.

## Tier 2: disk, network, SMP

A second kernel per architecture, `kernel-t2`, adds the block layer, SCSI disks, devtmpfs, each
machine's disk and network drivers, packet sockets and, where the machine has more than one CPU,
SMP (`config/tier2/`). `run.py --tier2` boots every machine once per profile, with the devices on
the QEMU command line and a switch per check on the kernel's (`wisp_disk=sda,vda`, `wisp_net=eth0`,
`wisp_smp=1`, which reach PID 1 as environment variables). PID 1 prints a `WISP-DISK`, `WISP-NET`
or `WISP-SMP` line after its result line; the batch output without them is unchanged.

| Machine | Disks | NIC | CPUs |
| --- | --- | --- | --- |
| `pc` (x86_64, i386) | PIIX3 IDE (`ata_piix`), virtio-blk | e1000; virtio-net in a second boot | 1, 2, 4 |
| `SS-10`, `SS-20` | ESP SCSI (`sun_esp`) | lance (`sunlance`) | 1, 2, 4 |
| `SS-5`, `SS-4`, `SPARCClassic`, `SPARCbook`, `LX`, `Voyager` | ESP SCSI | lance | 1 |
| `sun4u` | cmd646 IDE (`pata_cmd64x`), virtio-blk | hme (`sunhme`) | 1 |

- **Disk**: a 4 MiB raw image per disk, created for the run and filled with a pattern by `run.py`.
  PID 1 opens the raw device (no file system), reads and compares all of it, writes 1 MiB of its
  own pattern at 1 MiB, syncs, drops the page cache and reads it back from the device. `run.py`
  checks both CRCs and, after QEMU has exited, that the image has the guest's pattern at 1 MiB and
  is unchanged elsewhere.
- **Network**: ARP and 8 ICMP echoes (1,400 bytes of payload each) with QEMU's user-mode network
  at 10.0.2.2, which slirp answers itself: no host network or DNS involved, no DHCP (the guest is
  10.0.2.15). The kernel has no IP stack; PID 1 builds and checks the Ethernet frames on a packet
  socket, which keeps 385 KB of IPv4 out of the sparc32 kernel. The line has the ARP time and the
  round trips.
- **SMP**: one child per CPU, pinned with `sched_setaffinity`, runs the compute loop; every CPU must
  return the same CRC. SMP is in `kernel-t2` on x86 (`-smp 2` and `4`) and on sparc32 (`SS-10` and
  `SS-20` with OpenBIOS, `-smp 2` and `4`; the kernel drops futex, which nothing in wisp uses, and
  the same kernel boots the uniprocessor sun4m machines). sparc64 stays uniprocessor: QEMU's
  `sun4u` takes one CPU.

`run.py --shell --tier2` runs the shell with the first profile and adds `disk`, `net` and `smp` to
its script. The README in `e2e/wisp/` has the details, the sizes and the results.

## Building and running

Everything is in `e2e/wisp/` (see its README):

```sh
docker build -f e2e/wisp/Dockerfile -t wsh-wisp .
docker run --rm -v "$PWD/e2e/wisp:/wisp" wsh-wisp ./build.sh all
docker run --rm -v "$PWD/e2e/wisp:/wisp" wsh-wisp ./run.py --arch all --repeat 2
docker run --rm -v "$PWD/e2e/wisp:/wisp" wsh-wisp ./run.py --arch all --shell
docker run --rm -v "$PWD/e2e/wisp:/wisp" wsh-wisp ./run.py --arch all --tier2
```

The image has Debian 13's cross compilers, `linux-source-7.3` from trixie-backports and the
published `pve-qemu-kvm`. `run.py` prints one JSON object per run and a table: seconds from starting
QEMU to the kernel's first line, to PID 1, to the result line and to power-off, the loop time and
QEMU's peak RSS. `qemu-tci.sh` builds a TCI QEMU for the same targets; `run.py --qemu-dir` runs the
system under it.

## Kernel tiers

Four kernels build from the same `init.c` and PID 1; which ones `build.sh` makes depends on its
environment variables.

| Tier | Build flag | Kernel file | Adds |
| --- | --- | --- | --- |
| 1 | (default) | `kernel` | the batch run and, with `wisp=shell`, the interactive shell |
| 2 | (default; `TIER2=0` skips it) | `kernel-t2` | the block layer, SCSI/IDE/virtio disk drivers, devtmpfs, each machine's NIC driver, packet sockets, and SMP where the machine has more than one CPU |
| network | `TIER_NET=1` | `kernel-net` | IPv4, kernel DHCP (`ip=dhcp`) and Unix sockets on top of tier 2; IPv6, netfilter and wireless stay off |
| framebuffer | `TIER_FB=1` | `kernel-fb` | fbdev, the framebuffer console and a single 8x8 font on top of tier 2 |

## Network

`TIER_NET=1` builds `kernel-net`, layering a network config fragment on the tier-2 fragments and
reusing their packet sockets and NIC drivers (LANCE on SS-5, e1000 on `pc`, HME on `sun4u`). The
fragment adds IPv4, kernel DHCP and Unix sockets; IPv6, netfilter and wireless stay off. With
`ip=dhcp` on the kernel command line, the kernel configures the NIC from QEMU's user-mode network
(the `10.0.2.x` range) before PID 1 starts, so a `wisp=run` service gets a usable interface
without any networking code of its own.

The demo is a small HTTP service (`e2e/wisp/services/httpd/httpd.c`) started with `wisp=run`.
`service.py` packs the binary as `/test`, forwards a free loopback TCP port to the guest's port
8080, and after the serial listening marker checks two HTTP 200 replies containing the guest's
Linux release, machine name and request counters 1 and 2. It then checks the reply to `GET
/quit`, PID 1's exit marker and QEMU's exit status. sparc64 builds the same source with Debian's
cross `gcc` and a static glibc instead of uClibc-ng.

Measured with Linux 7.3.4 and QEMU 11.1.3 (TCG):

| Target (machine) | Service libc | To listening | `uname` machine in the HTTP replies |
| --- | --- | ---: | --- |
| sparc32 (SS-5) | uClibc-ng | 2.730 s | `sparc` |
| x86_64 (pc) | uClibc-ng | 4.217 s | `x86_64` |
| sparc64 (sun4u) | glibc | 2.694 s | `sparc64` |

All three returned HTTP 200 for both root requests and `bye` for `/quit`, then printed
`WISP-RUN v=1 exit=0 signal=0` and powered off.

## Framebuffer

`TIER_FB=1` builds `kernel-fb` for sparc32, sparc64 and x86_64, applying the framebuffer
fragments directly to tier 2: fbdev, the framebuffer console and a single 8x8 font. SS-5 uses
`FB_SBUS` with the `cg3` and `tcx` drivers; both PCI machines (`sun4u` and `pc`) use `DRM_BOCHS`
with `DRM_FBDEV_EMULATION` on QEMU's standard VGA display.

The shell's `fbtest` draws eight colour bars with a white border on `/dev/fb0` and reports the
mode; `mandel fb` draws the Mandelbrot set at the framebuffer's native resolution and reports its
iteration checksum; `keytest` prints key codes from a keyboard until Esc or a ten-second timeout.
sun4u's own PS/2 keyboard doesn't work: OpenBIOS's EBus device tree has no `kdmouse`/`mouse` node
for the `kb_ps2` child, and Linux's `i8042-sparcio` driver needs both IRQs, so it returns
`-ENODEV`. Its `kernel-fb` has a virtio keyboard driver instead, and QEMU gets
`-device virtio-keyboard-pci`, as on virt.

| Architecture (machine) | Display | `kernel-t2` | `kernel-fb` | Increase | Verified screendump |
| --- | --- | ---: | ---: | ---: | --- |
| sparc32 (SS-5) | cg3 and tcx | 3,315,656 bytes | 3,397,612 bytes | 81,956 bytes | 1024x768, 8 bpp, both passed |
| sparc64 (sun4u) | std | 4,125,576 bytes | 4,654,240 bytes | 528,664 bytes | 1280x800, 32 bpp, passed |
| x86_64 (pc) | std | 1,836,032 bytes | 2,016,256 bytes | 180,224 bytes | 1280x800, 32 bpp, passed |

`framebuffer.py` checks the colour bars and the Mandelbrot image pixel by pixel from QEMU
screendumps, checks the iteration sum, then sends key presses through QMP and checks for the
right Linux key codes.

## fbDOOM with Freedoom

`doom.py` packs a static fbDOOM as `/test` with Freedoom Phase 1 in an external initramfs and
starts it with `wisp=run -- @/demo.rsp`, a response file holding `-iwad /freedoom1.wad -nosound
-scaling 1 -timedemo demo1`. All three machines render the same centered 320x200 frame; the
timedemo skips keyboard setup entirely, including on sun4u.

Timedemo results (FPS is 35 x gametics / realtics; wall time includes firmware, Linux boot, the
game and power-off):

| Machine and display | Gametics | Realtics | FPS | Wall (s) |
| --- | ---: | ---: | ---: | ---: |
| SS-5 cg3 | 7117 | 886 | 281.15 | 32.19 |
| SS-5 tcx | 7117 | 886 | 281.15 | 32.21 |
| pc std | 7117 | 972 | 256.27 | 30.18 |
| sun4u std | 7117 | 4830 | 51.57 | 141.93 |

Each boot checks the demo's own command count (7,117), the reported FPS, a nonblank QMP capture
during playback and the successful exit and power-off. The game code (fbDOOM) is GPL-2.0 and
Freedoom is BSD-3-Clause; only the official Freedoom data is used, not id Software's WADs.

## Play DOOM

Two ways to play Freedoom in fbDOOM on wisp without building anything: on any Linux host with QEMU,
or as a VM on a Proxmox VE node. Both use the prebuilt framebuffer kernels and static fbDOOM
executables of the `wisp-fb` release (SHA-256 checked) and fetch Freedoom's WAD from Freedoom's own
release by a pinned URL and SHA-256. The game starts at the title screen at the largest integer scale
that fits the screen.

| Key | |
| --- | --- |
| arrows, Ctrl, space | move, fire, open (vanilla DOOM) |
| Esc, Enter | the menu (Esc, Enter, Enter, Enter starts episode 1) |
| `` ` `` (left of 1) | the FPS overlay on and off |
| Backspace | quit; wisp powers the machine off |

### On a Linux host

From a clone, with QEMU for the architecture and squashfs-tools installed:

```sh
cd e2e/wisp
python3 doom.py --arch sparc32 --play --from-release           # VNC on 0.0.0.0:5900
python3 doom.py --arch x86_64 --play --from-release --local    # a gtk/sdl window
python3 doom.py --arch aarch64 --play --from-release --fps --vnc :2 --sound
```

The machines are the wisp framebuffer machines: pc with standard VGA, the SS-5 with cg3 (`--display
tcx` for TCX), sun4u with standard VGA and virt with `bochs-display`, the last two with a virtio
keyboard. The pc uses KVM when it can, the others run under TCG. `--sound` uses PipeWire,
PulseAudio or ALSA when QEMU and the host have one, else no sound. `--kernel`, `--binary` and
`--wad` take local files instead of the downloads.

### In a PVE VM

On a node with the wsh-lab package (as root):

```sh
apt install squashfs-tools
wsh-lab wisp-vm sparc32 --doom --start
```

Then open the VM's Console in the web UI and play. `wsh-lab wisp-vm` creates the VM with the
machine's PVE profile (pc, SS-5 with OpenBIOS, sun4u or virt), the framebuffer as the noVNC console,
the kernel in `args` and the game on a read-only squashfs disk; `wsh-lab wisp-vm destroy --vmid N`
removes it again. Without `--doom` it makes a wisp shell VM instead. Details in
[Lab install targets](../lab-install/#wisp-in-a-vm-wisp-vm).

### The FPS overlay

`--fps` (or `` ` `` during the game) shows the frames per second in the top-left corner of the game
frame, drawn after the frame is scaled to the screen, so it stays sharp at any scale and never
touches DOOM's own 320x200 image. fbDOOM also prints `fbdoom: fps N` on the serial console once a
second while it is on. In paired timedemo runs with and without `-fps` on the pc and the SS-5 the overlay cost nothing measurable: the differences went both ways and stayed inside the run-to-run spread of the shared lab host.

FPS shown on the busy lab host under TCG, right after starting a game: SS-5 cg3 at 3x 40, pc at
4x 20 (69 at the title with KVM, in a PVE VM), virt at 4x 32, sun4u at 4x 10.

sun4u's own keyboard doesn't work under OpenBIOS, so its framebuffer kernel also drives a virtio
keyboard, as virt does.

## A real C library (uClibc-ng)

PID 1 itself stays on the kernel's nolibc, but a toolchain in `e2e/wisp/toolchain/` builds static
user programs against a real C library: uClibc-ng via Buildroot for sparc32 (SPARC V8, the same
target as `SS-5`) and x86_64. Debian's packaged 32-bit SPARC glibc and libgcc target V8+ even with
`-mcpu=v8`, which wisp's sparc32 kernel refuses, so sparc64 instead uses Debian's cross `gcc` with
a static glibc (`libc6-dev-sparc64-cross`); Buildroot's uClibc-ng config has no sparc64 target.

The Buildroot SDK images are published to GHCR
(`ghcr.io/hwinther/wsh-pve/wisp-toolchain-<arch>:2025.02.20`), and the manual
`publish-wisp-toolchain.yml` workflow also uploads `wisp-toolchain-<arch>.tar.xz` and its
`.sha256` file to the `wisp-toolchain` GitHub release; the wisp-test action (below) downloads this
SDK for `libc: uclibc` source builds without Docker.

| Target (machine) | SDK image build time | Unstripped `hello` size | ELF |
| --- | ---: | ---: | --- |
| sparc32 (SS-5) | 13 min 44 s | 84,484 bytes | 32-bit MSB SPARC (V8, `EM_SPARC`) |
| x86_64 (pc) | 15 min 52 s | 51,544 bytes | 64-bit LSB x86-64 |

Both `hello` binaries printed `WISP-HELLO v=1 checksum=0xed3258f703d97351 status=ok` and exited
with code 0 under the published `wisp-test-kit` kernel.

## The wisp-test GitHub Action

`.github/actions/wisp-test` is a GitHub Action built on wisp, for other projects' endianness and
alignment bugs: it builds a C program for sparc32 (big-endian, V8, `SS-5`), sparc64 or x86_64,
boots it under QEMU from Ubuntu's packages with `wisp=test` (or `wisp=run` for a service), and
passes or fails on the exit status. It needs no kernel build: `kit.sh` downloads a kit of the
tier-1 and network kernels and the nolibc headers from the `wisp-test-kit` release.

### Inputs

| Input | Default | What it is |
| --- | --- | --- |
| `sources` | | C files to build with the selected libc, whitespace-separated, globs allowed. Give this or `binary` |
| `binary` | | A static binary for the architecture, built by you (any C library) |
| `arch` | `sparc32` | `sparc32` (big-endian, V8, `SS-5`), `sparc64` (big-endian, V9, `sun4u`) or `x86_64` (little-endian, `pc`: the control, where a byte-order bug passes) |
| `libc` | `nolibc` | C library for source builds. Use `uclibc` on sparc32 or x86_64 for uClibc-ng |
| `toolchain` | | Local uClibc-ng SDK tarball to use instead of downloading it |
| `toolchain-url` | the architecture's tarball in the `wisp-toolchain` release | URL to download for a uClibc-ng build |
| `toolchain-sha256` | | Expected SHA-256 of the local or downloaded SDK tarball |
| `cflags` | | More compiler flags, after the default `-O2` |
| `args` | | Arguments for the program, whitespace-separated, no quoting |
| `mode` | `test` | PID 1 runs the payload with `wisp=test` or `wisp=run` (the `WISP-TEST` or `WISP-RUN` marker) |
| `network` | `false` | Boot the network tier's `kernel-net` with QEMU user networking and `ip=dhcp` |
| `forward` | | Guest TCP port to forward to a free port on runner loopback. Requires `network: true` |
| `ready` | | Bash extended regex matched against serial lines from the run start marker |
| `check` | | Bash command on the runner. Exit 0 passes, any other status fails; QEMU stops after the check |
| `timeout` | `60` | Seconds from starting QEMU to its exit |
| `machine` | | QEMU `-M` instead of the default |
| `qemu-args` | | More QEMU arguments, whitespace-separated |
| `kit` | | A kit directory or tarball to use instead of downloading `kit-url` |
| `kit-url` | the `wisp-test-kit` release of this repository | Where the kit comes from |
| `kit-sha256` | | The kit tarball's SHA-256; checked when set |
| `install` | `true` | `apt-get install` QEMU and the cross compiler when missing |

### Outputs

| Output | What it is |
| --- | --- |
| `result` | `pass` or `fail`, from the runner `check` when supplied, otherwise the guest exit status; build, boot and timeout errors give `error` |
| `port` | Runner loopback TCP port, also available as `WISP_PORT` to the check. The forward closes when QEMU stops |
| `exit-code`, `signal`, `signal-name` | The program's exit code and the signal that killed it, if any |
| `seconds`, `log` | Seconds from starting QEMU to its exit, and the console log's path |

### Examples

A big-endian unit test with nolibc:

```yaml
jobs:
  big-endian:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
```

## The LX and the Voyager

With the published 11.1.3-3+wsh6, `-M LX` stopped the kernel right after it switched to the zs
console: `qemu: fatal: Trap 0x07 (Unaligned Memory Access) while interrupts disabled` at
`tsetup_patch2` (three of three runs, also with `-m 64`); `-M Voyager` stopped the same way with
`Trap 0x02`. The PC was only where the damage ended. OpenBIOS gives every machine ID from 32 to 63
the SS-5's SBus devices, including the APC (`power-management` at `0x6a000000`), and Linux's
`apc` driver makes `apc_swift_idle()` the idle routine. QEMU has no APC there on the LX (a real
LX has none) or the Voyager, so the first idle (right after the console switch) read its register
with a data access error (trap 0x29 at `apc_swift_idle`). The load has no exception table entry,
and `do_sparc_fault()` dereferences the NULL that `search_exception_tables()` returns: each nested
fault takes a stack frame until the kernel stack has run down through the kernel's own text,
`do_sparc_fault` and `trap_setup` included, and QEMU stops in the overwritten trap entry code.
OpenBIOS patch 0027 (`openbios/patches/`) makes the APC node only on the machines that have the
chip there (SS-5, SS-4, SPARCClassic, SPARCbook). The published `pve-qemu-kvm` carries it since
11.1.3-3+wsh9: with that package, wisp boots on the LX and the Voyager, batch and shell; with
11.1.3-3+wsh8 both still stop as above (`Trap 0x07` on the LX, `Trap 0x02` on the Voyager). With an
older package, pass a patched `openbios-sparc32` with `--firmware` (QEMU's `-L`).

OpenBIOS patch 0029 leaves out the SS-5's CS4231 node (`0x6c000000`) where QEMU has no codec: on
the Voyager, the LX, the SPARCClassic and the SPARCbook (NetBSD 9.3 panicked on it on the LX;
`submodules/SPARC.md`, "SPARCstation LX with its own PROM"). wisp's kernels have no sound driver and
never saw the node. With OpenBIOS 0001-0029 given with `--firmware` and QEMU built from the pve-qemu
tree, all eight sparc32 machines passed batch, `--shell`, `--tier2` and `--shell --tier2` on the lab
host (36 boots, 2026-11-21).
