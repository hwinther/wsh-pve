The [sparc lab](https://github.com/hwinther/wsh-pve/tree/main/e2e/sparc) records every run it makes:
the serial console as an [asciinema](https://asciinema.org) recording and, when the guest has a
framebuffer, a short time-lapse video of it. These are from the lab's own runs against the
packaged QEMU, most of them through Proxmox VE; the weekly lab run keeps the recordings of every
case in its workflow artifact.

The recordings are documentary: short, time-compressed, from the lab's unattended runs. Pauses
longer than a second are cut, and the long ones also play faster (each caption says how much); the
marks on the progress bar are the lab's steps (hover for the title, or use `[` and `]` to jump
between them). Space pauses, the arrow keys seek.

The [Living museum](/guides/living-museum/) shows the same recordings by machine and operating system.

### SunOS 4.1.2 on SPARCserver 600MP

The oldest Sun release the lab runs: SunOS 4.1.2 (Solaris 1.0.1), the first release for sun4m, on
its first sun4m machine, the SPARCserver 600MP (`machine: SS-600MP`, [The SPARCserver
600MP](/guides/sparc/#the-sparcserver-600mp)). It needs pve-qemu patches wsh/0063-0065 (the 600MP's
VMEbus registers and the buffer memory its network chip works in) and OpenBIOS patch 0028 (the
device names 4.1.2 looks for), in pve-qemu-kvm 11.1.3-3+wsh13 and later. The same install as the
later SunOS 4 releases: the mini-root on the swap slice, suninstall's Quick install, then the check
boot (login, the system state, `halt`). Its `getty` sends even parity in bit 7, which the lab masks
before the terminal. SS-600MP, OpenBIOS, one CPU, 64 MB for the install, 256 MB after. Recorded
2026-11-22 with pve-qemu-kvm 11.1.3-4+wsh4 (install 2.4 min, check 0.9 min).

### SunOS 4.1.2 and Solaris 2.1 to 2.5.1 on SPARCserver 600MP with the Sun PROM

The same machine under Sun's own 600MP boot PROM (`bios: ss600mp.bin`, ROM Rev. 2.14; no package
has the image, see [The SPARCserver 600MP](/guides/sparc/#the-sparcserver-600mp)). QEMU gives the
PROM a configuration with `auto-boot?` false, so each start stops at `ok` on the serial console: the
install types `boot cdrom`, and the first boot and the check `boot disk`. SunOS 4.1.2 installs as
under OpenBIOS (the PROM boots the miniroot from its reboot string by itself). Solaris 2.1 to 2.5.1
each run the install of their SS-10 (2.1, 2.2) or SS-5 target unchanged: the CD as a disk, the same
screens and answers, End User. They need pve-qemu patch wsh/0190 (the MXCC stream registers' RDY
bit, which the kernels poll because this PROM offers `bcopy?`; without it each hung right after the
kernel's `clock gained ... days` warning). After 2.1's, 2.2's and 2.3's `init 5` the PROM reboots
with `-a` and stops at the boot program's `Enter filename`, which ends their boot recordings.
Solaris 2.6 and later refuse the machine by name. One CPU, 256 MB. Most of 2.5.1's install is its
Maintenance Update, so it plays at 4x, the other Solaris installs at 2x. Recorded 2026-11-27 with
the published pve-qemu-kvm 11.1.3-4+wsh37, qemu-server 9.2.24+wsh5 and pve-manager 9.3.1+wsh1, one
install at a time:

## Recording your own

Every `lab.py run` writes `serial.cast` (and `serial.fast.cast`, the pauses cut) next to its other
evidence, and `fb.webm` when the machine has a framebuffer; the run's `index.html` plays both offline.
`asciinema play serial.cast` plays a cast in a terminal. The lab's
[README](https://github.com/hwinther/wsh-pve/tree/main/e2e/sparc#recordings) has the details, and how
a recording gets onto this page.
